# 五步拆解标准作业流程 (Workflow)

将一篇文章转化为代码驱动的讲解视频，核心在于**把静态的文字逻辑，翻译成动态的代码行为与可感知的工程场景**。整个拆解流程分为以下五步：

---

## 第一步：材料解构（寻找代码能演绎的抓手）

阅读或抓取原文后，不要顺着原文流水账提炼，而是建立一个“技术戏剧张力清单”：

1. **现实痛点**：
   - 开发者或行业当下普遍怎么做？
   - 遇到了什么具体的瓶颈？（比如：延迟翻倍、Prompt 爆炸、维护灾难、幻觉频发）
2. **核心反直觉解法**：
   - 作者提出了什么打破常规的方案？（比如：别拆那么多 Agent，并回主循环用渐进式披露）
   - 这一解法的技术机理是什么？
3. **具象化支撑材料**：
   - 寻找具体的数字（例如：2x 速度提升、System Prompt 缩减 80%）；
   - 寻找真实踩坑的 Bad Case（例如：折叠后客服直接对客户下结论跳过审核）；
   - 寻找前后代码模式的改变（从硬编码编排到 Tool Search 动态加载）。

---

## 第二步：非对称大纲设计（包含确认门禁 1）

好视频的节奏不是由字数决定的，而是由认知冲击决定的。

1. **设置【确认门禁 1 · 时长与语言】**：
   - 必须先停下来与用户明确时长档位：
     - **2–3 分钟（精简单章）**：中文字数 650–880 字，只抓 1 个核心矛盾；
     - **3–5 分钟（标准深度）**：中文字数 1100–1400 字，3–4 幕节奏；
     - **5–8 分钟（专题长片）**：中文字数 1650–2200 字。
   - 确定语言（中文 / 英文），字数与句数从时长严格倒推，严禁超长。
2. **砍掉平铺直叙**：
   - 严禁出现“第一章、第二章、第三章”等长展开；
   - 挑一两个最核心的实操突破点（如：渐进式披露）深挖；
   - 次要的、常识性的概念（如：什么是单智能体）三言两语带过或融进开场。
3. **场景硬切设计**：
   - 避免无意义的过渡句（“接下来我们来看下一部分”）；
   - 利用画面切换、代码断点打点或控制台报错声效实现视觉与听觉上的硬切。
4. **交付大纲交由用户确认**：
   - 必须先向用户交付：时长规划、大纲骨架、拟采用的代码动效组件、核心矛盾点；
   - 用户确认后，方可进入逐字脚本撰写。

---

## 第三步：视觉代码组件映射

代码视频的精髓是用代码组件代替传统视频切片。每幕必须对应明确的 React / Remotion 组件：

| 叙事目标 | 推荐代码组件形态 | 画面表现 |
| :--- | :--- | :--- |
| **痛点/臃肿现状** | `<ArchitectureMap />` / `<NetworkGraph />` | 繁复混乱的调用拓扑图，节点间频繁握手，伴随延迟时钟不断增加 |
| **信息丢失/有损传递** | `<TelephoneGame />` / `<ContextLoss />` | 原始用户 Prompt 穿过层层子 Agent 时，字词被不断裁剪抹平的动效 |
| **技术机制演变** | `<CodeDiffViewer />` / `<RefactorTransition />` | 左边旧的编排器代码与右边干净的主循环代码做高亮对比与折叠动画 |
| **性能跃迁与收益** | `<MetricCard />` / `<LatencyBarChart />` | 动态柱状图或数字计数器从 8.4s 快速缩减到 4.1s，2x 绿色徽章弹起 |
| **动态检索过程** | `<ConsoleTerminal />` / `<ProgressiveLoader />` | 模拟真实 CLI 输出：初始仅加载技能清单，检测到需求后动态挂载 Schema |
| **工程边界/踩坑红线** | `<DecisionMatrix />` / `<EvalFailAlert />` | 红色警报组件跳出，显示真实回退用例，并切出红绿对比决策卡片 |

---

## 第四步：活人口语旁白创作（包含确认门禁 2 & 门禁 3）

视频不是论文朗读机。旁白必须具备极强的现场感和真实感：
1. 采用第一人称视角（“我们搭系统时经常遇到”、“说实话一开始我也觉得”）；
2. 严厉遵照 `references/narration-rules.md` 剔除所有 AI 八股与机械腔；
3. **空行分段 = 镜头分块**：每 2–4 句空一行，对应一个视觉镜头，严禁流水账；
4. **设置【确认门禁 2 · 解说词定稿】**：
   - 将完整逐字稿与分段贴给用户确认。必须定稿后才跑 TTS 和切分镜，因为后续帧号硬编码后改词成本极高。
5. **设置【确认门禁 3 · 配音引擎】**：
   - 确认配音音色（默认 edge-tts 云希原速），生成词级时间戳与毫秒级时间轴。

---

## 第五步：Remotion 规格化与动效三铁律（包含确认门禁 4）

在把分镜转化为 React/Remotion 代码时，必须严守工业级动效标准：

1. **持续动作 + 落位停留**：
   - 元素入场后不许完全静止 >3 秒，动词必须有微动作支撑（打字机、流光、呼吸、慢推）；
   - 末拍元素落位后，必须有 **30–45 帧（1–1.5s）稳定期**再离场，杜绝“刚落位就切走”；
2. **主角与光效克制**：
   - 每镜头一个视觉主角，主角高度 ≥170px，光只跟主角，配角不发光；
   - 扫光（`LightSweep`）全片 ≤2 处，只给核心概念首次登场。
3. **设置【确认门禁 4 · 前 30 秒样片预览】**：
   - 优先编写片头与第 1 镜头代码，快速测渲前 30 秒样片给用户确认；
   - 用户认可画风、字号、配音语速与节奏后，再大面积编写其余镜头组件。
4. **脚手架复用支持**：
   - 可直接使用 `~/.workbuddy-ai/skills/anything2explainer/template/` 中的 Remotion 4 脚手架与渲染脚本（`scripts/preview.sh` / `scripts/render.sh`）。
